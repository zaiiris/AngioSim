# AngioSim Hardware Protocol

## Current Arduino Logic

The current Arduino controller is a heart/pulse circulation controller generated by FLProg.

Source files:

```text
hardware/flprog/heart_pulse.flp
hardware/arduino/heart_pulse_flprog_generated.ino
```

The sketch currently controls local device behavior only. It does not yet send data to the backend.

## Signals

```text
D2  - pulse input from the circulation/flow sensor
D4  - menu/down button
D5  - value up button
D6  - value down / stop button
D7  - start/reset cycle button
D9  - inverse output
D13 - main circulation output
LCD - I2C 16x2 display at 0x27
```

Inputs `D4`, `D5`, `D6`, and `D7` use `INPUT_PULLUP`, so a pressed button is read as `LOW`.

## Stored Settings

The sketch uses EEPROM:

```text
address 0 - init marker 117
address 1 - continuous mode flag
address 2 - target milliliters
address 4 - target liters
```

Default values:

```text
continuous mode: off
target ml: 50
target liters: 0
```

## Runtime Values

```text
pulse_count      = number of pulses read from D2
volume_liters    = pulse_count / 2800.0
target_liters    = stored_liters + stored_ml / 1000.0
cycle_count      = number of started cycles
continuous_mode  = EEPROM boolean setting
```

## Backend Endpoint

Backend target:

```text
POST /api/hardware/events
```

Expected JSON:

```json
{
  "session_id": 123,
  "device_id": "heart-pulse-v1",
  "events": [
    {"sensor_name": "pulse_count", "value": 840, "unit": "pulses"},
    {"sensor_name": "volume", "value": 0.30, "unit": "L"},
    {"sensor_name": "circulation", "value": 1, "unit": "state"}
  ]
}
```

Optional future events:

```json
{"sensor_name": "pressure", "value": 48, "unit": "mmHg"}
{"sensor_name": "leak", "value": 0.12, "unit": "ml/min"}
{"sensor_name": "flow", "value": 1.42, "unit": "L/min"}
```

## Recommended Integration Path

1. Add `Serial.begin(115200)` to the Arduino sketch.
2. Emit one compact JSON line every 500-1000 ms.
3. Use a small desktop bridge script to read Arduino Serial and POST to `/api/hardware/events`.
4. The bridge should inject the active `session_id`, because the current Arduino sketch does not know which web session is active.

This keeps the Arduino simple and lets the web platform decide which training session receives the hardware data.
